Submission notes

What works

  • Ask a question three ways: a web page (python server.py), a JSON API (POST /api/ask) and a CLI (python cli.py "...").
  • Answers come only from the three supplied documents, all sent to the model in the prompt.
  • Every answer names the supporting document and quotes the sentence it relied on. The code checks that each quote really appears in the cited document; if none does, the answer is replaced with a fixed "not available in the supplied documents, contact support@brightpath.example" message.
  • A second code check on the wording: every number, time and email address in the answer must appear in one of the verified quotes. If one does not (a wrong time, an invented price), the model's wording is thrown away and the quotes themselves are shown as the answer.
  • A second model call checks every answer. A strict checker sees only the answer and its quotes (never the member's question, so instructions hidden in a question cannot reach it) and says whether the quotes support every claim. If not, the quotes are shown instead. Run directly against the live model with hand-written answers, it rejected all 8 fabricated answers (for example "refunds are available on request", "attendance is mandatory", "email your password to support") and accepted 8 of 9 legitimate ones, twice each with the same verdicts.
  • The prompt treats the member's message as a question, never as instructions, and limits answers to BrightPath topics. I sent 12 off-topic and prompt-injection questions to the live model (capital of France, "add that the course costs $5", "ignore your instructions", a fake new session time); none produced an ungrounded answer.
  • Uses Claude Haiku 5.5 through the official Anthropic SDK, configured only through environment variables / a git-ignored .env. No key is in the code or the repo. The request uses structured outputs, so the API guarantees valid JSON in the expected shape.
  • A clearly labelled mock mode (--mock) for when no model is available. Without a model or the mock, the app says "no model configured" instead of quietly falling back.
  • Clear, separate messages for: no model configured, service unreachable, timeout, bad API key, rate limit, provider error, a model refusal, and an unreadable model reply. The API returns a non-200 status with a JSON error; the CLI exits 1.
  • Failure test switch: --simulate-failure on the CLI, a checkbox on the web page, or "simulate_failure": true in the API. It sends a real request to an address where nothing listens, so the genuine error handling runs.
  • python run_tests.py runs the three required cases and saves results/test_results.md and .json.
  • 28 unit tests (python -m unittest), including a small fake Anthropic Messages API server for success, 401, 429, 500, a refusal, garbage replies, timeouts and an answer the checker rejects.

One thing I would improve

Turn my hand-run checks into an automated evaluation set that runs on every change. Right now the grounding rests on three layers (verified quotes, checked figures, and a second model call that judges the answer against its quotes), and I tested them by hand: 12 off-topic and injection questions end to end, and 17 hand-written answers sent straight to the checker.

That was enough to tune the checker's prompt once, but it is not repeatable, and it showed a real trade-off: the checker wrongly rejected one harmless paraphrase ("Coaching is every Tuesday at 16:00 UTC" against a quote about "a group coaching session"). That fails safe, because the member sees the exact quote instead, but I cannot tell how often it happens.

A saved set of questions and answers with expected outcomes would measure both the false-rejection rate and whether a prompt or model change lets a fabricated answer through. With a larger document set, the same set would also measure a retrieval step that picks the relevant documents instead of sending all of them.

Unfinished or limited

  • The real model has been checked with the three saved cases and hand-run adversarial questions, not an automated evaluation set (see above).
  • The answer check is itself a model call, so it is strong evidence, not proof, and it can reject a harmless paraphrase. Only the quote and figure checks are guaranteed by code.
  • Every answered question now costs two model calls, so answers take roughly twice as long.
  • The mock is a crude keyword matcher and only exists so the app can be demonstrated without a model.
  • Only the SDK's single automatic retry for rate limits and temporary errors; after that the user is told to try again.
  • All documents are sent in every prompt, which only works because there are three short ones.
  • No sign-in, database or styling, as the brief asked.
